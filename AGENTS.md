# AGENTS.md - scSpotlight Development Guide

## Purpose

scSpotlight is an R/Shiny application for single-cell RNA-seq analysis and visualization, built with the [golem](https://thinkr-open.github.io/golem/) framework.

Use this guide as the project operating manual for code changes, testing, performance decisions, and documentation updates. For recent frontend interaction decisions, UI behavior notes, and architectural rationale, see `DEVELOPMENT.md`.

## Non-Negotiable Constraints

### Scale Requirement

This application must efficiently handle millions of cells. All code contributions must consider performance implications for large datasets, especially 1M+ cells.

### Core Principles

- Treat low-memory execution as a primary design constraint for every data path.
- Avoid eager full-dataset materialization for metadata, reductions, expression, and other large transfers.
- Prefer path/query-plan based async work over passing live Seurat, BPCells, or Explore bundle objects into futures.
- Stream large server-to-browser payloads through chunked DuckDB/BPCells reads and Arrow IPC writers whenever possible.
- Keep browser-facing message contracts stable unless an intentional protocol migration is documented.
- Keep `DEVELOPMENT.md` updated whenever adding features, implementations, packaging workflows, validations, or major architectural decisions.

### Runtime Modes

- Analysis Mode is the full analysis workflow: `scSpotlight::run_app()`.
- Explore Mode is the read-only exploration workflow: `scSpotlight::run_app(runningMode = "explore")`.
- User-facing Explore Mode inputs should remain constrained to processed Explore artifacts documented in `DEVELOPMENT.md`.

## Architecture Patterns

### R To JavaScript Data Transfer

1. R writes versioned Arrow IPC files in the session temp directory.
2. R notifies JavaScript via `session$sendCustomMessage()`.
3. JavaScript fetches data through Arrow IPC helpers and may keep cold IPC buffers in a versioned client cache.
4. JavaScript decodes data to TypedArrays or compact metadata structures only when needed for rendering or analysis.

Large payloads should be generated by chunked writers. Avoid building full metadata, reduction, or expression payloads in memory when a path/query-plan plus streaming writer can produce the same browser contract.

### Backend Data Access

- Assay layers are read directly from the Seurat object, preferably through BPCells-backed on-disk matrices.
- Metadata is read from `object[[]]` for Seurat-backed Analysis Mode paths.
- Reductions are read from `Embeddings(object[[reduction]])` for Seurat-backed Analysis Mode paths.
- Explore Mode bundle data should be accessed from documented Parquet files through path/query-plan helpers.
- Expression payloads should use the selected Seurat assay layer or Explore bundle expression blocks, not a mirrored query store.

### Reactive Update Flow

Use indicator `reactiveVal()` counters to trigger cascading updates:

```r
metaUpdateIndicator <- reactiveVal(0)

# Trigger update:

metaUpdateIndicator(metaUpdateIndicator() + 1)
```

## Performance Requirements

### Rendering Thresholds

Adjust deck.gl rendering parameters based on cell count. The implementation lives in `srcjs/modules/deckScatter.js`.

| Cell Count | Point Size | Opacity | Pickable |
| --- | --- | --- | --- |
| < 15,000 | 4 | 0.8 | true |
| 15K - 50K | 3 | 0.7 | true |
| 50K - 500K | 2 | 0.6 | true |
| 500K - 1M | 1 | 0.5 | true |
| 1M - 2M | 0.5 | 0.4 | true |
| > 2M | 0.2 | 0.2 | false |

### JavaScript Performance Rules

- Use `deck.gl` for WebGL-accelerated main scatter plots. Do not use canvas or SVG for the main 1M+ cell scatter path.
- Use TypedArrays such as `Float32Array`, `Int32Array`, and `Int16Array` for large numeric data.
- Store categorical data as index arrays with level lookup, not repeated string arrays.
- Debounce resize handlers, typically at 250ms.
- Purge webR `shelter` after each operation to free memory.
- Avoid DOM manipulation in tight loops.

### R Performance Rules

- Use BPCells for on-disk assay storage and direct Seurat layer access.
- Avoid loading full matrices into memory.
- Use Arrow IPC for versioned binary transfer between R and the browser.
- Use `ExtendedTask` and `future_promise()` for non-blocking async operations.
- Prefer path/query-plan futures to passing live Seurat, BPCells, or Explore bundle objects into futures.
- Use `scattermore::geom_scattermost()` for R-generated plots when cells exceed 30K.

## R Development Guidelines

### Shiny Module Pattern

```r
#' ModuleName UI Function
#' @noRd
#' @importFrom shiny NS tagList
mod_ModuleName_ui <- function(id) {
  ns <- NS(id)
  tagList(
    # Use ns() for all input/output IDs
  )
}

#' ModuleName Server Functions
#' @noRd
mod_ModuleName_server <- function(id, reactive_args) {
  moduleServer(id, function(input, output, session) {
    ns <- session$ns
    # Module logic
  })
}
```

### R Style

- Use `snake_case` for functions, for example `query_duck_expr`.
- Use `camelCase` for Shiny inputs/outputs, for example `selectedAssay`.
- Use `camelCase` for reactive values, for example `seuratObj` and `metaProcessed`.
- Use `req()` for input validation in observers.
- Use `validate(need(...))` for user-facing validation.
- Use `tryCatch()` for operations that may fail.
- Use `isTruthy()` to check for valid values.

### R Documentation

- Use roxygen2 with `@noRd` for internal functions.
- Use `@importFrom` for specific imports and `@import` sparingly.
- Document exported functions in the current backend helpers as reference.
- Run `devtools::document()` after changing exported functions or roxygen imports.

## JavaScript Development Guidelines

### Module System

Use ES modules with Vite bundling:

```javascript
import { functionName } from "./modules/moduleName.js";

export const myFunction = () => { ... };
export class MyClass { ... }
```

### JavaScript Style

- Use `camelCase` for variables and functions.
- Use `PascalCase` for classes, for example `ScatterDeckController`.
- Use `camelCase` or `UPPER_SNAKE_CASE` for constants, reserving uppercase for true constants.
- Use `camelCase` for DOM element IDs.

### Shiny Integration

```javascript
// R to JS
Shiny.addCustomMessageHandler("message_type", (msg) => {
  // Handle message from R
});

// JS to R
Shiny.setInputValue("inputName", value, { priority: "event" });
```

### webR Operations

```javascript
const result = await shelter.evalR(`R code here`);
await shelter.purge();
```

Always use `async`/`await` with webR and purge the shelter after each operation.

## Feature Development Checklist

1. Add new Shiny modules with `golem::add_module(name = "ModuleName")` when appropriate.
2. Add new JavaScript modules in `srcjs/modules/` and import them from `srcjs/index.js`.
3. Rebuild JavaScript with `pixi run build-js` for production bundle changes.
4. Test with datasets of varying sizes, including 1K, 100K, and 1M+ cells when feasible.
5. Profile performance for large datasets before merging high-impact data-path changes.
6. Keep `DEVELOPMENT.md` updated whenever adding features, implementations, packaging workflows, validations, or major architectural decisions.

## Git Workflow Policy

### Branch Roles

- `main` is the production branch and must always remain deployable.
- `dev` is the integration/staging branch for ongoing feature work.
- `feature/*` branches are short-lived and should be created from `dev`.

### PR Flow

1. Create `feature/*` from `dev`.
2. Open PR from `feature/*` to `dev`.
3. Address review feedback in the same branch, push new commits, and keep the PR updated.
4. Merge to `dev` only after checks pass.
5. Promote tested changes via PR from `dev` to `main`.

### PR Summary Expectations

- PR summaries should preserve implementation context for future review.
- Include overall goal, server-side changes, client-side changes, performance impact, correctness/safety improvements, caching/state-management changes, and validation performed when relevant.
- Prefer repository file references and concrete behavior changes over vague summaries like `refactor` or `cleanup`.
- When a PR changes interaction contracts or architectural patterns, update `DEVELOPMENT.md` with the rationale and behavior rules.

### Review Feedback Handling

- Reply to each review thread with one of: fixed, partially fixed, or not changed.
- When fixed, reference the commit SHA or file path.
- When not changed, provide a short rationale based on scope, risk, compatibility, or performance.
- Resolve review threads only after posting a clear reply.

### Merge And Rollback Rules

- Prefer squash merge for feature PRs unless preserving commit history is important.
- Delete merged `feature/*` branches.
- If a change in `dev` is problematic, revert it in `dev` before promoting.
- If a change reaches `main` and must be undone, revert the merge commit on `main`.

### Sync Rules

- Keep `dev` synchronized with `main` after each release merge to avoid drift.
- Keep active feature branches rebased or merged with `dev` regularly to reduce conflicts.

## Docker

The Dockerfile uses the Pixi base image in the build stage, installs locked `default` and `prod` environments, builds JavaScript assets in `default`, installs the R package into `prod`, and copies only the activated `prod` environment into the runtime image. The final container runs `Rscript` directly and does not require Pixi at runtime.

```bash
docker build -t scspotlight .
docker run -p 8081:8081 scspotlight
```

The container's default `CMD` starts the app in Analysis Mode on port 8081.

## webR VFS Library Rebuild

Use this when webR package availability changes or when refreshing browser-side R libraries.

```bash

# Build package repo + VFS image in a clean toolchain container

mkdir -p /tmp/scspotlight-webrbuild
docker run --rm -v "/tmp/scspotlight-webrbuild:/output" -w /output ghcr.io/r-wasm/webr:main \
  Rscript -e "install.packages('pak', repos='https://cloud.r-project.org'); \
              pak::pak('r-wasm/rwasm'); \
              library(rwasm); \
              add_pkg(c('ggplot2','scales','scattermore','dplyr','patchwork','cowplot'), dependencies = NA); \
              make_vfs_library(compress = TRUE)"

# Deploy VFS files into app static assets

cp /tmp/scspotlight-webrbuild/vfs/library.data.gz inst/app/www/webr/vfs/library.data.gz
cp /tmp/scspotlight-webrbuild/vfs/library.js.metadata inst/app/www/webr/vfs/library.js.metadata

# Rebuild JS bundle after VFS update

pixi run build-js
```

Notes:

- `dependencies = NA` is the recommended `add_pkg()` setting for hard dependencies.
- If `compress = TRUE`, mount `www/webr/vfs/library.data.gz` and ensure `library.js.metadata` contains `"gzip": true`.
- If compression causes issues, fall back to `make_vfs_library(compress = FALSE)` and mount `www/webr/vfs/library.data`.

## Vite Configuration

`vite.config.js` handles:

- Entry point: `srcjs/index.js`.
- Output: `inst/app/www/index.js` in UMD format.
- Externals: Shiny, jQuery, and waiter from R-provided globals.
- Source maps for debugging.
- Terser minification for production.

`vitest.config.js` handles:

- jsdom test environment.
- Global test utilities such as `describe`, `it`, and `expect`.
- Module resolution aligned with Vite.
